## §0 The problem (as found live, 2026-07-19)

Three symptoms, one shared root cause: **nothing in the app uses AI to extract line
items from a bill.**

1. **Assistant chat**: rep attaches a bill PDF and says "Gupta Medicos ke liye order
   banao is bill se". Gemini classifies `start_order(party_query="Gupta Medicos")`
   correctly — but `start_order` is deep-link-only *by V4 design* ("never extract
   line items" was an explicit V2/V4 rule to keep the intent path cheap). The New
   Order dialog opens with the party preselected and **zero line items**. The rep
   retypes the whole bill by hand. This defeats the entire point of attaching it.
2. **Plan executor**: same gap surfaces at the end of the (now-fixed) create-party→
   first-order chain — the order opens for the right (new) party but empty.
3. **Manual "Import Excel/CSV" on Orders**: for PDF/image files this runs
   `src/lib/file-extract.ts` (raw text extraction) + `src/lib/import-orders.ts`'s
   `parseOrderLine()` — a **regex heuristic** ("last number on the line = amount,
   second-last = rate, first integer = qty"). Real-world PDF text extraction scrambles
   column order and merges cells, so the output is garbage or nothing: the user's
   screenshots show `Demo Bill.pdf` → "44 rows, 1 column", `Demo Bill jpg.jpeg` →
   "29 rows, 1 column", and — most damning — `Invoice_INV_2026_003.pdf`, **an invoice
   generated by this very app's own PDF exporter**, mapping `party_name → "tal Rs. 1"`
   and `product_name → "Acrowell Labs Pvt. Ltd. INVOICE INV · Date:"`.

Meanwhile, Gap A testing (2026-07-18, see corpus README) already **proved** Gemini
3.1 Flash Lite reads these exact documents correctly end-to-end — party names,
products, batch, qty, expiry all extracted right, via the live Worker. The model can
do this; the app just never asks it to.

## §1 What V5 delivers

One new capability, wired into three places:

1. **A new Worker endpoint `POST /extract`** that takes a bill (PDF or image) and
   returns structured invoices + line items as JSON. No intent classification — pure
   document extraction with a fixed schema.
2. **Assistant flow**: bill attached + `start_order` intent (direct OR inside a plan,
   including the deferred create-party→order chain) ⇒ line items are extracted and
   the New Order dialog opens **prefilled** — party, invoice no/date, and every line
   item (product, batch, expiry, qty, free, MRP, rate, disc%, GST%). Rep reviews and
   saves; nothing is written without the existing dialog review.
3. **Manual import**: PDF/image files route through `/extract` instead of the regex
   parser. Because the schema is fixed, the column-mapping screen is **skipped** for
   AI-extracted files — straight to the existing preview/edit step. Excel/CSV keep
   the current deterministic parser (it works and is free).

## §2 Hard rules (non-negotiable)

- **Do NOT touch `prompt.ts` / `FUNCTION_DECLARATIONS` / `STATIC_SYSTEM_PROMPT`.**
  The cached /chat prefix is at 8,637 tokens — adding a line-items schema there
  risks the 9K–17K Gemini caching dead zone and forces the full cache ritual.
  `/extract` must be a separate module with its own small prompt. If you find
  yourself needing a prompt.ts change, STOP and ask the user first.
- All V4/build-spec §8 rules stand: no migrations (V5 needs ZERO — verify this
  stays true; if not, stop and ask), no `git push` (user pushes via GitHub
  Desktop), every write keeps a visible review step (here: the New Order dialog /
  import preview ARE the review), RLS is the boundary, Worker never touches the DB.
- Honesty rule: extraction is very good but not infallible — never present
  extracted numbers as authoritative. The review step is mandatory, not skippable.
- TEST- prefix on any data created during acceptance testing + cleanup list.

## §3 Worker: `POST /extract` (new module, `acrowell-ai-worker/src/extract.ts`)

- **Auth/limits/usage**: identical to `/chat` — Supabase JWT check, same per-user
  daily message + weighted-token caps, same usage object in the response so the
  frontend logs it to `assistant_usage` (action: `"extract_order"`).
- **Request**: `{ image: { mimeType: string, dataBase64: string } }` — same file
  shape the frontend already sends to /chat. PDFs raw; images already downscaled
  by the existing `downscaleImage` path (proven sufficient in Gap A tests).
- **Gemini call**: `gemini-3.1-flash-lite`, **no tools** — use `responseMimeType:
  "application/json"` + `responseSchema` (structured output). Its own system prompt
  (~500–800 tokens, NOT the cached /chat prefix; do not create a cachedContents for
  it — extraction calls are rare and the uncached cost is trivial). Prompt should
  say: extract EVERY line item; use null for genuinely absent fields, never invent
  values; dates → YYYY-MM-DD; strip currency symbols/commas from numbers; a page can
  contain multiple invoices — return one entry per invoice.
- **Response schema** (also enforce server-side after parse — coerce numbers, clamp
  `line_items` to 100/invoice and `invoices` to 20, ISO-validate dates):

```json
{
  "invoices": [{
    "invoice_no": "string|null",
    "invoice_date": "YYYY-MM-DD|null",
    "party_name": "string|null",
    "line_items": [{
      "product_name": "string",
      "hsn": "string|null", "pack": "string|null", "batch": "string|null",
      "expiry": "YYYY-MM-DD|null",
      "qty": 0, "free": 0, "mrp": 0, "rate": 0, "disc_pct": 0, "gst_pct": 0,
      "amount": 0
    }],
    "subtotal": 0, "gst_total": 0, "grand_total": 0
  }]
}
```

- **Worker response**: `{ extraction: <schema above>, usage: { input, output, cached } }`.
  Errors: 400 no/oversized file (cap ~15 MB base64), 422 if Gemini returns no
  parseable invoices (frontend shows a friendly Hinglish message), plus the existing
  401/429 paths.
- **Stage-1 acceptance (before ANY frontend work)** — curl the live endpoint the same
  way this session tested /chat (Supabase password-grant token + base64 file via
  Bash; see the build-spec Correction block session for the exact working pattern),
  with the user's three real files:
  - `~/Downloads/Demo Bill.pdf`
  - `~/Downloads/Demo Bill jpg.jpeg`
  - `~/Downloads/Invoice_INV_2026_003.pdf` (the app's own generated invoice —
    **this one especially must come back perfect**: INV-2026-003, 2026-07-19,
    Sunrise PCD Franchise, its 2 items with correct qty/rate/amount)
  Record each result verbatim in the build-status update.

## §4 Frontend: assistant flow (`use-assistant.ts`, `assistant-chat.tsx`, `orders.index.tsx`)

**4a. Fire extraction at the right moment.** In `send()`, after the intent arrives:
if an image/PDF was attached to THIS message AND the resolved outcome contains a
`start_order` (directly, as a plan step, or as a deferred plan step), call
`/extract` immediately (async) and store the promise + result in a ref
(`pendingExtractionRef`). Push a lightweight status message ("Bill se items nikal
raha hoon…" → on success "Bill se N items mile — order kholne par bhar dunga.").
Do NOT extract for other intents (create_lead from a visiting card etc. — waste).

**4b. Consume at navigation.** In `confirmAction`'s `start_order` case (the single
funnel both direct confirms and plan-resumed confirms already pass through): before
navigating, `await` the pending extraction (timeout ~20s; on timeout/failure,
navigate party-only + toast "Bill se items nahi nikal paya — order khaali khulega").
Write the prefill to `sessionStorage` key `acrowell_order_prefill_v1`:
`{ partyId, invoice_no, invoice_date, items: [...], ts: Date.now() }` — consume-once
(the reader deletes it). Then navigate to `/orders?party=<id>` as today.

**4c. Read + prefill.** `orders.index.tsx` already auto-opens `NewOrderDialog` when
`?party=` is present (the W4C fix). Extend: on auto-open, read+delete the
sessionStorage key; if present, `partyId` matches, and `ts` is <10 minutes old, pass
the payload into `NewOrderDialog` via a new optional `prefill` prop.

**4d. Dialog prefill semantics.** In `NewOrderDialog`: map each extracted item to a
line-item row. Fuzzy-match `product_name` against the products catalog (reuse the
existing product-resolution helper the CSV import path already uses — do not write a
new matcher): matched → set `product_id` and keep the **bill's** rate/qty numbers
(the bill is the source of truth for this transaction; catalog rates are defaults,
not overrides); unmatched → the dialog's existing free-text product row with the
extracted name. Fill batch/expiry/qty/free/mrp/rate/disc%/gst% from extraction.
Prefill Invoice No + Invoice Date too **only if** the extracted values are non-null
(otherwise keep the auto-generated number). Everything stays editable — this dialog
IS the review step.

**4e. Plan-chain caveat.** For the create-party→order chain, the party on the bill
is the party just created, so no party matching against extraction is needed — the
prefill's `partyId` is whatever `start_order` is navigating with. Extraction runs
once at send time and survives in the ref until consumed, so the resume path needs
no extra wiring beyond 4b. Verify this explicitly in acceptance.

## §5 Frontend: manual import (`orders.index.tsx` `handleFile`, `import-orders.ts`)

In `handleFile`, branch by file type:
- `.csv/.xlsx/.xls/.xlsm` → **unchanged** (deterministic, free, works).
- PDF/image → call `/extract` (auth via the existing supabase session; show the
  existing `busyMsg` progress UI: "AI se bill padh raha hoon…"). Flatten
  `invoices[]` into rows with the exact canonical headers the mapper already
  produces for parsed bills (`invoice_no, invoice_date, party_name, product_name,
  hsn, pack, batch, expiry, qty_billed, qty_free, mrp, rate, disc_pct, gst_pct,
  amount` — see the existing `parseOrderFromExtract` output shape). Because these
  headers are canonical, **skip step 2 (mapping) entirely** and jump straight to
  the preview step with an auto-identity mapping. Multi-invoice PDFs work free of
  charge: the existing `rowsToInvoices` grouping by invoice_no already splits them.
- Keep `file-extract.ts`/`parseOrderLine` as the offline fallback ONLY when
  `/extract` errors (429/500) — with its existing "couldn't find line items" toast.
  Do not delete the old path; do stop routing to it first.
- `.doc/.docx/.html` (rare): leave on the old path unchanged; out of scope.

## §6 Cost & caching impact (tell the user these numbers in the handoff)

- /chat cached prefix: **untouched** (8,637 tokens, no ritual needed).
- Per-extraction: ~600–800 static prompt tokens + document (~260 tokens/PDF page)
  + output (~30–60 tokens/line item), all at Flash-Lite prices ⇒ roughly
  **₹0.01–0.05 per bill**. Runs only when a file is attached to an order-ish
  request or uploaded in import. Negligible at any realistic volume.

## §7 Staged rollout — each stage gates before the next

**Stage 1 — Worker `/extract`.** Build + deploy + the §3 curl acceptance on all three
real files. No frontend changes yet.

**Stage 2 — Assistant flow (§4).** Acceptance, live in browser as manager:
(a) attach `Demo Bill.pdf` + "Gupta Medicos ke liye is bill se order banao" → New
Order opens with Gupta Medicos AND the bill's line items filled; (b) the flagship
chain: attach bill + "is bill se naya party banao aur unka pehla order start karo"
→ party dialog → save → order confirm → New Order opens for the NEW party with the
bill's items; (c) regression: text-only "start order for gupta" still opens
party-only with no stale prefill (consume-once + fromImage gating verified);
(d) extraction-failure path shows the toast and still opens party-only.

**Stage 3 — Manual import (§5).** Acceptance: import each of the three files via
the Orders import button → preview shows correct rows without a mapping step →
commit ONE as a TEST- order → verify → note it in the cleanup list. Also verify a
normal CSV import still works unchanged.

**Stage 4 — Docs.** Update the build-spec (new V5 build-status block: what shipped,
verbatim acceptance results, deviations), corpus README (one line: extraction is a
separate endpoint, not part of the intent vocabulary), memory file, and hand back:
push list, cleanup list, open items.

## §8 Out of scope for V5 (explicit)

- `record_purchase` (goods-inward) prefill from supplier bills — same machinery
  would work; deliberately deferred until the user asks.
- Auto-creating unmatched products from a bill ("Acmol-650 catalog mein nahi hai,
  add kar dun?") — a natural follow-up, but it stacks a second dialog into the
  flow; defer.
- Any change to /chat's prompt, vocabulary, or the 608-row corpus work.
- OCR quality work for terrible photos — Gemini gets what it gets; the review
  step is the safety net.
